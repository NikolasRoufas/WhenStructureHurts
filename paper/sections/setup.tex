\section{Experimental Setup}
\label{sec:setup}

\paragraph{Questions.}
All questions come from one frozen sample of the development splits (seed~1), fixed before any generation: 100 MuSiQue questions stratified by hop count (2/3/4: 34/33/33), 100 2WikiMultiHopQA questions stratified by question type (25 each of comparison, inference, compositional and bridge-comparison), and, as secondary datasets, 50 HotpotQA questions (25 bridge, 25 comparison), 50 HoVer claims (2/3/4 hops) and 50 FEVER claims (25 \textsc{supports}, 25 \textsc{refutes}). Eligibility rules (gold evidence available; for QA, a reasoning order available) are applied before sampling, and the fifteen questions used during prompt development are excluded. We first run the 200 MuSiQue and 2WikiMultiHopQA questions (the \emph{focused pilot}) and then the complete 350-question set (the \emph{expanded pilot}); generations shared between the two are served from a cache keyed on the full prompt and every decoding setting, so they are identical by construction.

\paragraph{Answerer.}
The answerer is Qwen2.5-7B-Instruct \citep{qwen2024qwen25} at the pinned revision \texttt{a09a3545}, in bfloat16, with greedy decoding, at most 64 new tokens and at most 4{,}096 input tokens. Auxiliary models are bge-small-en-v1.5 (dense retrieval in B4), ms-marco-MiniLM-L6-v2 (reranking), nli-deberta-v3-xsmall (relation prediction) and nli-deberta-v3-small (grounding), all pinned \citep{he2023debertav3}. Experiment~0 also uses the 7B model as its claim extractor.

\paragraph{Hardware and batch size.}
All generations run on a single NVIDIA RTX~5000 Ada GPU with 32\,GB of memory (CUDA~13.0, PyTorch~2.12.1, Transformers~5.12.1). The server has a second GPU of the same type, but it is reserved for another service and was not used, so every reported run is a single-GPU run. We generate with batch size~1. In a preflight on development questions that are excluded from all reported runs, batched greedy decoding in bfloat16 changed 3 of 8 7B outputs relative to unbatched decoding, including one answer, whereas float32 batched and unbatched outputs were identical and unbatched bfloat16 outputs were identical across runs. Batching would therefore have made a question's output depend on which other prompts shared its batch, which in turn depends on prompt lengths and hence on the representation. Batch size~1 removes this source of variation at a cost in throughput.

\paragraph{Statistics.}
The unit of analysis is the question. For each contrast we report the paired difference in question-level EM over the questions available in both conditions, with a 95\% percentile bootstrap interval (2{,}000 resamples, seed~0) and a two-sided bootstrap $p$-value \citep{efron1993bootstrap}; R2 seeds are averaged within a question before pairing. Every contrast also reports the number of questions whose two evidence blocks are byte-identical (for example, R5 equals R1 when the graph-derived order coincides with the dataset order), the same estimate restricted to the remaining \emph{informative} pairs, and the paired difference in coverage. Protocols, datasets, budgets, policies and edge strata are never pooled. As secondary analyses we report the exact McNemar test on discordant pairs \citep{mcnemar1947} and the standardised paired effect $d_z$. All these procedures, the primary metric and the primary contrasts were fixed in a pilot protocol before any generation. Because both stages are exploratory pilots on a sample that was also used to design the study, no test is treated as confirmatory and we do not apply the Holm correction \citep{holm1979} that the protocol reserves for a confirmatory run; an interval that contains zero is reported as inconclusive, never as evidence of equivalence.
